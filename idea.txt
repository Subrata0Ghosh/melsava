# 3. EXPERIENCE COMPLETION AND HOST-CONFIRMED ATTENDANCE

The reconnect selection must never be available to users who merely joined an experience but did not attend.

Implement a secure host attendance confirmation workflow.

### Host workflow

When an experience has ended:

1. The host opens the Experience Hub or host management view.
2. A host-only attendance action becomes available.
3. Show the actual joined participants.
4. The host marks the people who attended.
5. The host reviews the attendance list.
6. The host submits attendance confirmation.
7. The experience becomes completed.
8. Confirmed members receive the attended membership status.

Use the existing `experiences.host_id`, `experience_members.status`, and `experience_status` schema where possible.

### Security requirements

- Only the actual experience host can submit attendance.
- The experience must have ended before it can be completed.
- Cancelled or draft experiences cannot be completed through this operation.
- Only users who previously had an eligible joined membership may be marked attended.
- Waitlisted and cancelled members cannot be marked attended without a valid prior membership.
- The host cannot mark members from another experience.
- Regular participants must never be allowed to set their own attendance status directly.
- Prevent arbitrary membership changes by modifying IDs or other membership fields.

Use a new transactional SECURITY DEFINER database function with a fixed search_path and explicit auth.uid() validation.

Suggested function:

complete_experience_and_mark_attendance(
    p_experience_id UUID,
    p_attended_user_ids UUID[]
)

You may adjust the function signature after checking the existing schema.

Use row locking where necessary.

The operation must be atomic and idempotent.

Replace broad client-side attendance update permissions with a controlled server-side operation where appropriate.

Do not trust Flutter to enforce attendance eligibility.

Only explicitly confirmed attendees can continue to post-experience selections.

# 6. FIX THE EXISTING MUTUAL MATCHING SQL FUNCTION

IMPORTANT: Review the existing `process_mutual_connections()` function in migration 003.

The current function has two serious problems:

1. It treats any two positive choices as a match, even if the connection intentions differ.
2. It prioritizes the more romantic choice if either person selects dating.

This violates mutual consent.

Replace or supersede the old implementation using migration 007.

### Correct matching logic

Create a connection ONLY when:

- User A attended the same completed experience.
- User B attended the same completed experience.
- User A submitted a final selection.
- User B submitted a final selection.
- A selected B.
- B selected A.
- Both selected the same compatible connection type.
- Neither user blocked the other.
- Both accounts remain eligible.
- No duplicate connection already exists.

For the initial MVP, use exact matching:

A selects Friendship + B selects Friendship = Friendship connection.

A selects Activity Partner + B selects Activity Partner = Activity Partner connection.

A selects Explore Dating + B selects Explore Dating = Explore Dating connection.

A selects Friendship + B selects Explore Dating = NO CONNECTION.

A selects No Connection + B selects any option = NO CONNECTION.

Do not choose the stronger or more romantic option automatically.

Do not expose private choice records.

### Server-side connection creation

For a valid mutual connection:

1. Create a canonical connection record using the existing user_a_id < user_b_id constraint.
2. Create a conversation record if one does not already exist.
3. Create both conversation membership records.
4. Associate the original experience.
5. Insert an in-app notification for each user if the existing notification system supports it.
6. Return the actual mutual connection result.

All database writes must happen inside one transaction.

Prevent duplicate connection records and duplicate conversations.

If the users were already connected from a previous experience, do not create another connection or another conversation.

Return only the authenticated user's legitimate connection results. Never return every pair of matches in the group to one caller.

### Function permissions

Review the SECURITY DEFINER function permissions.

Restrict execution explicitly.

Do not leave an unrestricted function callable by anonymous clients or arbitrary authenticated users.

Check grants, revoke unnecessary execution rights, validate auth.uid(), and ensure that the function cannot be used to process another group's selections or reveal other people's preferences.

Do not trust client-supplied chooser_id values. Derive the chooser identity from auth.uid().
