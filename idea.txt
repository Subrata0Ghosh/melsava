# PART 2 — REQUIRED PHASE 4 SECURITY PREFLIGHT

Before Phase 5, fix these issues in the existing Phase 4 implementation.

Review migration 013.

### A. Message INSERT policy

The current messages INSERT policy permits direct insertion by an authenticated conversation member.

Message insertion should use the validated send_conversation_message RPC.

Remove or restrict direct client insertion and revoke unnecessary INSERT privileges.

### B. Message UPDATE policy

The current messages UPDATE policy allows a non-sender to update message rows beyond the is_read field.

Prevent recipients from changing:
- Message content.
- Sender ID.
- Conversation ID.
- Created timestamp.

Only the validated mark_conversation_read RPC should change read receipts.

Use appropriately restricted database privileges and RLS.

Do not rely on Flutter to restrict which database columns a client can modify.

### C. Conversation access

Review can_access_conversation(UUID).

Ensure it validates:
- Authenticated conversation membership.
- Valid mutual connection for direct conversations.
- Correct conversation participants.
- Account suspension state.
- Blocks in either direction.

### D. Realtime and inbox

Verify active conversation subscriptions, cleanup, duplicate-message protection and incoming message behaviour.

Add suitable realtime updates or invalidation for the inbox thread list.

Do not create multiple subscriptions for a single active conversation.

### E. Error handling

Do not silently turn RPC errors into an empty inbox, zero read count or success-looking state.

Preserve error information for Riverpod and the UI.

Use a new numbered migration after checking the existing migration history and deployed migrations.

Do not modify previously applied migrations.

# PART 7 — FIX ACCOUNT DEACTIVATION AND DELETION

IMPORTANT SECURITY TASK.

Existing auth_repository.deleteAccountPermanent() has a dangerous fallback:

If delete_user_account fails, it attempts to delete only the public profiles record and then signs the user out.

This does not guarantee deletion of the underlying Supabase Auth account.

Remove this fallback completely.

Never display a successful deletion message unless actual account deletion has been confirmed.

### Permanent account deletion

Use a secure Supabase Edge Function.

Suggested name:

delete-account

Requirements:

1. Verify the authenticated user's JWT server-side.
2. Confirm the request is for the authenticated user only.
3. Require an appropriate recent reauthentication or fresh-authentication confirmation.
4. Verify the user explicitly confirmed permanent deletion.
5. Clean up user-owned avatar objects in Supabase Storage.
6. Verify existing database foreign-key cascades.
7. Delete or appropriately anonymize associated personal data according to the deletion policy.
8. Remove the actual Supabase Auth user using the server-side Admin API.
9. Return an explicit result only after the operation succeeds.

Store SUPABASE_SERVICE_ROLE_KEY only as a Supabase Edge Function secret.

Never expose it through:
- Flutter.
- GitHub.
- .env files included in the APK.
- Dart constants.
- Client-side RPC parameters.

The client must never be allowed to delete arbitrary user accounts.

### Failed deletion

If the Edge Function fails:
- Do not delete only the profile row.
- Do not automatically sign the user out.
- Preserve a clear error message.
- Allow a safe retry.
- Log server errors without exposing private user information.

Only clear local authentication state after the server confirms deletion or a separately verified successful sign-out.

### Deactivation

If full deactivation is supported, implement it properly with a real server operation.

Otherwise remove the nonfunctional deactivation option rather than displaying a fake success.

Do not add a paid deletion provider.
