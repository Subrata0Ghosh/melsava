# PART 2 — REQUIRED PHASE 3 HARDENING

Before Phase 4, fix the following two important issues through a new migration.

Do not modify previously applied migrations.

Use the next available migration number after inspecting the repository.

### A. Host attendance completion

Inspect:

complete_experience_and_mark_attendance(UUID, UUID[])

Current issue:
The function checks that the experience has started but does not check that its scheduled duration has finished.

It also does not reject every invalid attendee ID before reporting success.

Fix:

1. Require an authenticated host.
2. Lock the experience row.
3. Verify the correct host.
4. Reject cancelled and draft experiences.
5. Verify current time is at or after the scheduled end time using starts_at and duration_minutes, or the actual end-time field if the schema has one.
6. Validate the entire attendee array.
7. Reject duplicate user IDs.
8. Reject IDs that do not belong to an eligible joined membership.
9. Do not silently ignore invalid attendance IDs.
10. Keep the operation atomic.
11. Do not allow regular members to update their own attendance status.

If duration information is missing, return a clear validation error rather than completing the experience prematurely.

If the experience is already completed, implement a safe, clearly defined idempotent result. Do not let an ordinary retry silently alter finalized attendance records.

### B. Private choice submission concurrency

Inspect:

submit_post_experience_choices(UUID, JSONB)

Current concern:
Concurrent reciprocal submissions can happen before either transaction sees the other submission.

Use an appropriate transaction-level lock, such as locking the parent experience row with FOR UPDATE before checking and inserting the submission.

This should serialize post-experience submissions for the same experience and prevent missed mutual connections.

Also inspect the current UI payload.

- Validate all submitted participant IDs.
- Reject self-selection.
- Reject participants who did not attend the same experience.
- Reject invalid choice types instead of silently converting them.
- Reject duplicate participant entries.
- Ensure submission semantics are consistent with the current UI's No Connection defaults.
- Permit an empty selection only when there are genuinely no eligible peers.
- Prevent retry from creating duplicate connections, conversations or notifications.

Preserve the existing exact compatibility rules:

Friendship + Friendship = Friendship.

Activity Partner + Activity Partner = Activity Partner.

Explore Dating + Explore Dating = Dating.

Different intentions = No connection.

Never automatically upgrade the relationship intention.

Add regression tests for these two hardening changes.

Always use auth.uid().

Return actual connections belonging to the authenticated user.

Required response information where supported:

- connection_id
- conversation_id
- partner_id
- partner_name
- partner_avatar
- partner_bio
- connection_type
- experience_id
- experience_title
- last_message
- last_message_at

Requirements:

- Include either side of the canonical user pair.
- Return only mutual connections.
- Exclude blocked relationships.
- Exclude suspended accounts.
- Join approved public profile fields only.
- Join the actual originating experience.
- Join the associated conversation.
- Include a genuine last message when one exists.
- Return a useful empty list for an account with no connections.
- Sort by most recent conversation activity, then connection creation.

Do not return private profile information.

Do not fabricate compatibility scores.

Do not fabricate online status.

Do not return fake last messages.

10. Insert the message using the real sender ID.

13. Return the actual inserted message.
14. Do not allow the caller to specify sender_id.

Do not trust client-provided timestamps or sender identity.

- Valid associated connection.

- No suspended participant.

Apply it to:

- Conversation reads.
- Conversation member reads.
- Message reads.
- Any other relevant policies.

For sending messages, use the validated server function.

For read receipts, use mark_conversation_read().

Do not expose conversation membership data to unrelated users.

### Blocking behaviour

The existing block action must have an immediate backend effect.

Once User A blocks User B:

- Neither can send new messages to the other.
- The blocked conversation must no longer be returned in normal inbox queries.
- The conversation should no longer appear in mutual connection discovery.
- Realtime message access must stop for the blocked pair.
- Existing connection records must not be re-created automatically.

Do not delete historical messages simply because a user blocks someone, unless the actual account deletion policy requires it.

The UI must clearly confirm whether the block succeeded.
