## 4. FIX THE OLD MUTUAL MATCHING LOGIC

IMPORTANT.

Review process_mutual_connections() in migration 003.

The existing function incorrectly selects the more romantic intention when users choose different intentions.

Replace or supersede it safely.

New exact compatibility rules:

| User A | User B | Result |
|---|---|---|
| Friendship | Friendship | Friendship connection |
| Activity Partner | Activity Partner | Activity connection |
| Explore Dating | Explore Dating | Dating connection |
| Friendship | Explore Dating | No connection |
| Friendship | Activity Partner | No connection |
| Explore Dating | Activity Partner | No connection |
| No Connection | Any | No connection |
| One-sided choice | No reciprocal choice | No connection |

A connection is allowed only if:

- Both people attended the same completed experience.
- Both submitted their final selections.
- A selected B.
- B selected A.
- Both selected the exact same connection type.
- Neither person blocked the other.
- Both accounts remain eligible.

Do not infer a romantic intention.

Do not use intention priority.

Do not create connections based on a user's profile preferences alone.

### Connection creation

For an eligible mutual pair:

1. Normalize user IDs so user_a_id < user_b_id.
2. Check for an existing connection.
3. Create one connection if none exists.
4. Create one conversation.
5. Create two conversation_members records.
6. Associate the connection with the experience.
7. Create an in-app notification for each participant.

Use database transactions, unique constraints and conflict-safe inserts.

Never create duplicate connections or conversations when users retry.

If a pair is already connected from an earlier experience, reuse its existing connection and conversation according to the existing unique-user-pair design.

Do not silently overwrite the original connection context.

### Protect the matching function

Do not leave the old function publicly executable with arbitrary experience IDs.

Restrict its permissions.

Perform matching only through the validated submission workflow or an appropriately protected internal database helper.

Revoke unnecessary EXECUTE permissions from PUBLIC and anon.
