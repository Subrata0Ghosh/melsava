# 2. THE PRODUCT CONCEPT

The main product loop is:

DISCOVER AN EXPERIENCE → JOIN A SMALL GROUP → PARTICIPATE → CHOOSE PEOPLE TO RECONNECT WITH → MUTUAL CONNECTION → CONTINUE THE RELATIONSHIP.

A user should not need to swipe through hundreds of profiles to find someone.

Instead, users discover activities they genuinely want to participate in, meet other people with compatible interests and intentions, and decide privately who they would like to connect with afterwards.

The app must support different adult intentions:

1. Genuine friendship
2. Activity partner
3. Casual dating
4. Meaningful dating
5. Serious relationship
6. Marriage-minded connection
7. Open to discovering where a connection goes

Users may select multiple intentions and choose a primary intention.

Do not force all users into a romantic experience. Friendship must be a complete and valuable use case.

Do not promise that matching guarantees compatibility or a successful relationship.

**Target market:** India first, followed by international markets.

**Initial audience:** Adults aged 18 and above. Do not impose an arbitrary upper age limit. Respect individual age and discovery preferences.

**Launch strategy:** Start with one city or concentrated community, then expand.

# 3. THE DIFFERENTIATING FEATURE

The most important feature is the post-experience mutual connection system.

Example:

Four people attend a coffee and conversation activity.

After the activity, each participant privately sees the eligible people they met.

Each participant can select:

- Connect as friends
- Connect as activity partners
- Explore dating
- No connection

Selections must remain private.

Example:

Person A privately selects Person B for friendship.

Person B privately selects Person A for friendship.

The system creates a connection and opens a private conversation.

If only one person selects the other, nothing happens.

For dating, both participants must independently select a compatible dating intention. A friendship selection must never automatically become a romantic match.

For group experiences, process each participant pair separately.

Never publicly reveal who rejected or did not select somebody.

Do not allow somebody to purchase, unlock or force another person's consent.

This mutual-choice experience is the core product feature and must be implemented correctly on the backend, not just visually in Flutter.

# 8. SUPABASE DATABASE DESIGN

Use PostgreSQL with UUID primary keys, foreign keys, timestamps, indexes and appropriate constraints.

Create the following initial tables:

1. profiles
2. profile_private
3. interests
4. profile_interests
5. intentions
6. profile_intentions
7. activity_categories
8. experiences
9. experience_sessions
10. experience_members
11. experience_prompts
12. experience_answers
13. post_experience_choices
14. connections
15. conversations
16. conversation_members
17. messages
18. blocks
19. reports
20. moderation_actions
21. device_tokens

Use auth.users as the authentication identity.

Store public profile information separately from private account information.

Never return private data through public discovery queries.

Avoid storing exact dates of birth unless there is an appropriate legal and product need. If required, store it in a private server-controlled location.

Create migrations in a version-controlled folder.

Create seed SQL for activity categories and example experiences.

Enable Row Level Security on every user-data table.

Create specific least-privilege RLS policies.

Examples of the security model:

- Users can update their own profile.
- Users cannot update another person's profile.
- Public discovery returns only approved profile fields.
- Private account fields are not readable by other users.
- Users can read messages only in conversations they belong to.
- Users cannot create a connection unilaterally.
- Users can see only their own post-experience choices.
- A blocked relationship prevents new interaction.
- Reports must not reveal the reporter's private identity to the reported user.
- Users cannot modify their own moderation status.

Do not trust the Flutter client to enforce mutual selection, age eligibility, event capacity or moderation restrictions.

Implement critical operations server-side using PostgreSQL functions or protected Edge Functions.

Make the mutual connection operation transactional and idempotent.

Never use the Supabase service_role key in the Flutter client.

Use only the Supabase publishable key on the client, protected by correctly configured RLS.

Keep all private keys out of Git.

Create a safe environment configuration approach using Flutter build-time configuration.

# 9. MUTUAL CONNECTION BUSINESS LOGIC

Implement the post-experience choice flow carefully.

For each completed experience:

1. Retrieve eligible participants.
2. Show only information approved for post-experience selection.
3. Save each participant's private selections.
4. Prevent repeated submissions or invalid participant IDs.
5. Compare both sides of each potential connection.
6. Check that the selected connection types are compatible.
7. Check that neither participant blocked the other.
8. Create one connection for each valid mutual selection.
9. Create a conversation for that connection.
10. Notify both users without disclosing rejected selections.

Use a database unique constraint to prevent duplicate connections.

Make the workflow safe against duplicate requests and concurrent selections.

The system must never reveal one person's selection to another before mutual agreement.
