# MELSAVA — PHASE 2: LIVE EXPERIENCE DISCOVERY, JOINING & MY CIRCLES

## Main Objective

Implement a fully working, Supabase-powered experience discovery and joining system.

Users must be able to discover real published experiences, view their details, join or join a waitlist, cancel participation, and manage their upcoming and past experiences.

**Keep the current MELSAVA UI, design system, navigation structure and existing architecture. Do not rebuild the app.**

This phase should turn the existing Discover and Experiences screens from demo/local-data screens into real, working features.

## 2. Fix the Small Remaining Phase 1 Data-Integrity Issue

Before starting Phase 2, check the profile onboarding completion logic.

Currently, failures while saving profile interests or intentions may be caught and logged without preventing onboarding from being marked complete.

Fix this carefully:

- Required profile data must be saved successfully before onboarding is marked complete.
- Do not silently ignore failed interest or intention saves.
- Display a useful error and allow the user to retry.
- Avoid creating duplicate interests or intentions on retry.
- Do not send users to Discover if required onboarding data is missing.
- Use a database transaction/RPC if appropriate for the existing schema. Otherwise, only set the completion flag after every required save succeeds.

Do not redesign or rebuild onboarding.

## 3. Connect Discover to Real Supabase Data

Replace the local sample experience repository with a real Supabase-backed repository.

Requirements:

- Fetch only published experiences.
- Exclude cancelled, draft and already-passed experiences from the upcoming discovery feed.
- Load real experience titles, descriptions, categories, cover images, dates, times, city, venue or online status, host information and available capacity, according to the existing schema.
- Show the current user's actual membership status.
- Use proper pagination or a sensible query limit.
- Avoid loading unnecessary data.
- Handle missing images and optional fields gracefully.
- Use the existing Riverpod provider/repository architecture.

Both Discover and Experiences must use the same source of real experience data.

Do not leave fake sample data as a production fallback.

Development seed data is acceptable for local testing, but keep it clearly separated from real production content.

## 4. Implement Useful Discovery Filters

Use simple, understandable filters that work with the real database:

- Search by experience title or description.
- Category.
- City.
- Upcoming date.
- Online or in-person.
- Experiences with available places.

Use the city and interests already saved in the user's profile where appropriate.

Recommendations should be simple and inexpensive:

- Give priority to experiences matching the user's saved interests and city.
- Show other upcoming experiences when there are no direct matches.
- Never hide all experiences just because there is no exact match.
- No paid AI API, external recommendation service, GPS service or map API.

Do not add complicated filters or redesign the Discover UI.

## 5. Experience Details

Make the existing experience details screen display real Supabase information.

Show the fields available in the actual schema:

- Experience name and description.
- Category.
- Date and time.
- Duration, when available.
- City and venue, or online status.
- Host information.
- Participant count and available places.
- Cancellation information.
- Clear Join or Waitlist action.

The displayed capacity and membership status must reflect the latest database state, not a hard-coded number.

Use the existing design components and maintain the current visual style.

## 6. Real Join and Capacity Management

Replace local `toggleJoin()` behaviour and simulated success delays with real database operations.

Joining must be handled securely on the server.

Inspect the existing migrations and implement a new migration for an atomic database join operation if one does not already exist.

The join operation must:

- Require an authenticated user.
- Confirm that the user's profile and adult eligibility are complete.
- Confirm the experience is published and still eligible for joining.
- Prevent duplicate membership.
- Check capacity using the current database state.
- Add the user as joined when a place is available.
- Add the user as waitlisted when the experience is full, if waitlisting is supported by the existing schema.
- Return a clear result to the app.

Capacity checks must be atomic and safe when multiple users try to join at the same time. Do not depend only on a client-side participant count.

Use the existing `experience_members` statuses and database design where possible.

If the existing waitlist model supports it, implement FIFO waitlist promotion when a joined member cancels.

Cancellation and waitlist promotion must be handled safely on the server to avoid duplicate promotions or overbooking.

Tighten RLS so users cannot bypass the capacity rules by directly inserting or changing membership records from the client.

Use a new numbered migration based on the latest existing migration. Never edit migrations that may already have been applied.

Do not use a Supabase service-role key in Flutter.

## 7. Improve the Join Confirmation Flow

Reuse the current join confirmation sheet and preserve its design.

- Show the selected experience clearly.
- Confirm the action before joining.
- Show actual joining progress.
- Show success only after Supabase confirms the operation.
- Show a clear error and retry option if it fails.
- Display the correct Joined or Waitlisted result.
- Prevent repeated taps while the operation is processing.

Inspect the existing “Your Intent” selection. Do not show a choice that is not actually saved or used. If the current schema does not support an experience-specific intention, keep the join confirmation simple and rely on the user's saved profile intentions. Do not default users to a romantic or dating intention.

## 8. Make My Experiences / My Circles Functional

Turn the existing screen into the user's real experience-management area.

Use actual membership records from Supabase.

Organize the screen into simple sections or tabs:

- Upcoming: experiences the user has joined.
- Waitlisted: experiences where the user is waiting for a place.
- Attended: completed experiences the user attended.
- Past: relevant completed or expired experiences.

Show useful status labels and allow the user to open the corresponding details.

Allow cancellation of upcoming participation with confirmation.

Do not display hard-coded participants or fake membership records.

Keep the experience-management UI simple and consistent with the existing app.

## 9. Loading, Empty and Error States

Every database-powered screen must support:

- Loading state.
- Empty state.
- Error state.
- Retry.
- Successful action feedback.
- No internet or connection failure.

Use natural, friendly messages.

Examples:

- "No experiences found yet."
- "Try another category or check back soon."
- "You have joined this experience."
- "You're on the waitlist."
- "We couldn't complete that action. Please try again."

Do not use fake success messages.

Avoid unnecessary animations and expensive dependencies.

## 10. Security and Database Requirements

Review all relevant RLS policies before implementing the features.

Ensure:

- Users can only manage their own memberships.
- Users cannot create memberships for another user.
- Users cannot directly change their own membership to attended.
- Capacity cannot be bypassed.
- Only eligible users can join.
- Only published experiences can be joined.
- Waitlist order is preserved if implemented.
- Public experience details do not expose private user information.
- Database functions have appropriate permissions.
- No service-role key or secret is included in the Flutter app.

Reuse existing tables and functions where possible.

Create only the migrations and indexes genuinely needed for this phase.
